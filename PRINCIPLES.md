# Принципы устройства инструкций и доков слоя агента

Выведены из рефактора живого проекта (три шага ревизии за неделю работы: корень, инструкции репо кода, слой
целиком). Шаблон собран по ним; при правке скелета сверяться с этим списком. Метод ревизии — в конце.

## Инструкции
- **Корневой `AGENTS.md` — тонкая точка входа** (≤ ~100 строк): продукт и стек, маршрутизация по типу запроса
  (код — через трекер; ресёрч и правка знаний — без задачи; отдельные действия — командами), правила, карта.
  Никаких таблиц из репозиториев кода (модули, архитектура, команды сборки) — они живут в `<repo>/AGENTS.md`.
- **Маршрутизация по типу запроса вместо «сценария 99 %» и «лестницы чтения».** Список «прочти всё» толкает агента
  грузить всё; что читать — определяется запросом.
- **Состояние не живёт в инструкциях.** Текущий этап, «сейчас», «по факту» — только в `ROADMAP.md` (снимок из
  трёх пунктов: фокус, ждёт решений, заморожено) и в трекере; обновляет промпт закрытия задачи. Инструкция — правила
  и карта.
- **У правила один владелец; копия — ссылка и крючок, без пересказа.** Иначе версии расходятся за неделю
  (правило «кто ставит ADR accepted» жило в пяти формулировках). Проверка ревизии: каждый абзац инструкции —
  правило, команда или пересказ; пересказ → ссылка с крючком.
- **История — в журнал, норма — в правило.** Рассказы «в задаче N так потеряли патч» из инструкций убираются; id
  в скобках допустим.
- **Число в правиле — только если оно само правило** (градация, допуск). Свойства инструмента (шум замера, время
  сборки) — в его техдок.
- **`<repo>/AGENTS.md` — правило один раз**: команды блоком без пояснений, правила их применения — отдельным
  разделом, чеклист — только пунктами-ссылками. Таблицы и списки фактов о коде — в техдоке темы, инструкция ссылается.
- **`<repo>/AGENTS.md` не ссылается на личный слой.** Единственная такая ссылка — `CLAUDE.local.md` (не в git):
  человек, клонирующий только репо, не должен видеть чужую раскладку.
- **Термины стандартные.** Агент воспроизводит лексику собеседника, поэтому терминологию надо фиксировать явно:
  необычное слово из обсуждения не разносится по докам и коду.
- **Бюджет контекста измеряется, а не ощущается.** Сумма байт файлов, которые грузятся на типовую команду до первой
  строки задачи, — число; дубли и байки режутся первыми. Ориентир из практики: ~60 КБ кириллицы на `/next-task`
  (семь файлов) — это уже порядка 25 тысяч токенов.
- **Трение называть, а не молчать.** Инструкция, док или скрипт, который помешал, — файл в `friction/` с порогом
  (послал не туда, прочитан впустую, грабли съели ≥ 2 попытки, скрипт упал не по вине задачи) и поле в отчёте.

## Знания
- **Три уровня доков**: «что и почему» (концепция, дорожная карта), «как устроено» (состав — по проекту),
  «обоснования и журналы» (ADR, обсуждения, сырьё). Индекс — таблица «владеет / когда читать», формулировка «когда
  читать» повторяет корень, не расширяет его.
- **Матрица «что изменилось → куда писать»** — один владелец на каждый вид изменения; ход работы — в трекер, не в доки.
- **Техдок не пересказывает сигнатуры.** Перечни полей и методов — doc-комментарий в коде; в техдоке — то, чего из
  кода за минуту не видно: инварианты, контракты, порядок, владение, «почему так», точки расширения.
- **У контракта один файл-владелец**, остальные ссылаются. Таблица — для коротких ячеек; строка длиннее ~300 знаков
  — подраздел со списком.
- **Карта «код → техдок» — один источник, из которого читает скрипт-гейт** (третий столбец таблицы — триггер);
  добавил файл темы в карту — гейт подхватил. Гейт битых ссылок — в каждом репозитории с доками.
- **Техдок инструмента живёт с инструментом** (в репо, под его гейт); в слое знаний — «что и зачем меряем».
- **Снимок ≠ журнал.** Доки целей держат «сейчас: число, задача», история — датированный журнал строкой на задачу
  (`grep ID` должен возвращать строку, а не обрывок абзаца). Append-only журнал помечает отменённое
  (`[отменено ID]`), не стирает.
- **Решение одной строкой** в концепции: «решение → ADR → где описано»; текст живёт у владельца.
- **ADR**: варианты обязательны; принятый не редактируется; заменённый удаляется, когда код и доки переведены;
  принимает человек — или агент при явном выборе человека из обсуждения.
- **Обсуждение переработки** (несколько подтем, несколько решений) — папка `discussions/<тема>/` между сырьём и
  ADR: «как сейчас → решено → открыто → связи»; закрыто — удаляется, итог в ADR и уровне 2. Обсуждение, тема
  которого — сам слой агента, ведётся там же.
- **Сырьё не проверяется гейтом ссылок** и не правится.

## Трекер и команды
- **Состояния — в правилах, шаги — в промпте.** Таблица «статус → где лежит → кто переводит → что ещё» в правилах
  трекера; порядок действий исполнителя — в `/next-task` со ссылками на таблицу. Один владелец у переходов.
- **`/next-task` = взять + сделать + сдать**; начатую задачу — продолжить. Отдельная команда сдачи не нужна.
- **Команд столько, сколько разных действий.** Команда, повторяющая скрипт или другую команду с аргументом, —
  сливается или удаляется.
- **Шаблон файла владеет структурой и подсказками; правила — тем, чего шаблон не выражает.** Форматы входящих —
  TEMPLATE-файлы, не README у каждой папки.
- **Служебные файлы — по содержимому, не по шаблону**: `INDEX.md` только при вложениях или порядке чтения;
  `.gitkeep` не держит папки «на будущее».
- **Постановка — язык поведения, самодостаточна, снимок, а не журнал**; длина не ограничивается лимитом строк, а
  правилом «механика, не реализация»: реализация — в `implementation.md`. Тело, которое уезжает в удалённый
  трекер, не содержит локальных путей и имён слоя.
- **Экономия чтения — правило промпта**: постановка → комментарии → реализация; техдоки по карте темы по одному;
  вывод вызова > ~200 строк — в файл; разведка одним способом (сам или подагент, не оба).
- **Правило и скрипт говорят одно.** Правило «пути от корня» — и `links.sh` красит относительные и короткие;
  правило «проверь перед коммитом» — хук pre-commit, из инструкций оно уходит.

## Скрипты и манифест
- **Манифест — данные для скриптов, не документ для агента.** Никаких структур, которые репо знает лучше (модули,
  архитектура); значения вроде префикса — сид для инструкций при инициализации.
- **Профили вместо мёртвого кода.** Remote-трекер, ADR, несколько сервисов — ставятся по ответам `init.sh`, не
  лежат «на всякий случай»; профиль без второго проекта, которому он нужен, не заводится (оценки и внешние наборы
  скиллов убраны по этому правилу). Серверный CI — по требованию, не в скелете.
- **Команда — это процедура.** Команда из одной фразы (запустить скрипт, правило реакции) — строка в `AGENTS.md`,
  не шим и промпт.
- **Пустые ключи в манифесте не нужны** — скрипты переживают их отсутствие.
- **Allow-лист совпадает с правилом**: правило велит звать скрипты абсолютным путём — `setup-local.sh` добавляет
  абсолютную форму в личные настройки.
- **Шаблон и развёрнутые проекты расходятся в обе стороны, сверка — скриптом, не глазами.** Инструментальные файлы
  (скрипты, промпты, шаблоны задач, правила трекера) и в проекте, и в скелете; проект их специализирует (имя репо,
  термины), шаблон обобщает. Единственный способ не терять правки — трёхстороннее слияние от маркера последней
  сходимости (`sync.sh`): дельта шаблона ложится поверх специализации, дельта проекта — поверх плейсхолдеров.
  Проектные файлы (засеянные) из сверки исключены списком, а не угадыванием.


## Метод ревизии (повторять раз в несколько недель)
1. Посчитать бюджет: байты файлов, которые грузятся на `/next-task` до первой строки задачи.
2. `grep` каждого правила по слою: где владелец, где копии; копии → ссылка с крючком.
3. Пройти инструкции по абзацам: правило / команда / пересказ / байка / число.
4. `git log --stat` по докам целей и дорожной карте: файл с десятками правок за неделю — журнал под видом снимка.
5. Сверить правило и скрипт (пути, проверки, хук); сверить команды на дубли со скриптами.
6. Находки → обсуждение `discussions/` с README-картой шагов; применённое → сюда, если принцип общий.
