# decisions/ — ADR (Architecture Decision Records)

Одно решение — один файл `NNNN-slug.md`, id `ADR-NNNN`. Скрипт — `workspace/bin/docs/adr.sh`
(`new <slug> [название] | list | check | accept <ID> | supersede <старый> <новый> | index`). Команда агента — `/adr`.

## Когда писать
Для решений, которые дорого откатить: язык и фреймворк, границы модулей и сервисов, форматы данных и контракты,
целевые цифры, способ деплоя. Тест: «если это изменится, сколько кода придётся переписать». Не для имён, стиля,
локальных приёмов — это `AGENTS.md` сервиса.

## Правила
- **В момент решения, не после.** Черновик `proposed` обсуждается, затем `accepted` или `rejected`. Ретроспективный
  ADR для уже принятого решения допустим, помечается в контексте («зафиксировано задним числом»).
- **Принятый ADR не редактируется.** Передумали — новый ADR, `adr.sh supersede <старый> <новый>`: старый получает
  `superseded` и ссылку, новый — `supersedes`. Опечатки и ссылки править можно, смысл — нет.
- **Варианты обязательны.** Самое ценное — что рассмотрели и почему отбросили; без этого спор начнётся заново.
- **Статус `accepted` ставит человек** (`adr.sh accept`), агент готовит только `proposed`.
- **Связь с работой.** Задача, которой нужно решение, указывает `depends: [ADR-NNNN]` — `trk.sh ready` считает её
  заблокированной, пока ADR не `accepted`. ADR указывает породившие/зависимые задачи в `tasks:`.
- Принятое решение отражается там, где агент его прочитает первым: карта/правила в `AGENTS.md`, концепция,
  контракты — по матрице `workspace/docs/README.md`. ADR — обоснование, не единственное место.

Статусы: `proposed | accepted | rejected | superseded`. Формат — `TEMPLATE-adr.md`.
